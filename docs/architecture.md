# CompaSpot MVP v2 — Architecture

CompaSpot remains an ASP.NET Core + PostgreSQL + Angular modular monolith deployed on the existing AWS/Cloudflare topology. No microservice migration, Kubernetes, Redis, broker, or general framework adoption is implied by MVP v2.

## Dependency rule

```text
Domain → Application → Infrastructure / API / Angular UI
```

Domain does not depend on AWS, OpenAI, SMS/email implementation, Angular, EF Core implementation details, or transport concerns. Controllers/endpoints stay thin; application/domain services own use-case logic.

## Data and delivery rules

- Use explicit DTOs, boundary validation, centralized authorization, `ProblemDetails`, async/cancellation, `HttpClientFactory`, bounded timeout/retry, structured logs and correlation IDs.
- Reads use projections, `AsNoTracking`, pagination and indexes driven by real query patterns. Keep migrations additive, small and reversible.
- Important operations are idempotent where appropriate.
- Invitation delivery uses transactional persistence of Invitation + Outbox record, followed by a background worker. Retries must not lose or duplicate contact.
- Cache only stable reference data such as categories/templates/service-area lookups. Do not cache active offers, workflows, permissions, claims, notification preferences or user-specific AI responses.
- Company representation is resolved through active `CompanyMembership`, not a global active-company claim. This foundation is additive: `SupplierProfile` and its shared-key compatibility constraint remain unchanged until a concrete future requirement justifies a broader migration.
- A provider notification is never addressed to a company ID. The application resolves its active CompanyMembership users in the same write operation and creates one personal notification per distinct recipient. Conversations use the same membership check for company-side access; message authors remain User IDs.
- Supplier Discovery persists `OpportunityMatch` as an auditable, per-need relation to exactly one registered company or unregistered candidate. Registered provider matching remains authoritative; candidate relevance is deterministic from category compatibility and county, then requires a separate Administrator decision for that exact opportunity. The decision never sends contact automatically.
- Admin web discovery is a bounded two-stage extension of Supplier Discovery: an explicit Need-context action, or an exact Admin **Firme** lookup after internal search is insufficient, performs limited external evidence gathering, then a tool-free strict-JSON qualification pass. `SupplierDiscoveryService` orchestrates `SupplierSearchIntent`, a shared `CategoryDiscoveryProfile`, geographic planning, independent Google Places/Web collectors, deterministic evidence merging and the qualifier. Google Places and OpenAI Web Search are independent sources; source warnings do not discard usable evidence from the other source. Geographic expansion is local → nearby → county only when the preceding tier is insufficient, and the merger persists that provenance. `SupplierWebDiscoveryRun` persists only provisional commercial evidence/results and telemetry; it does not bypass candidate review, opportunity approval or outreach policy. A company lookup never creates an `OpportunityMatch`.
- Outreach is an additive Supplier Discovery concern: `SupplierOutreachContact` records manual or email contact attempts, `SupplierContactSuppression` prevents later contact (including rediscovery), and email links are invitation- and opportunity-specific. SMTP is called only after the attempt/invitation is persisted, then delivery is recorded without holding the database transaction across the network call.

## AI contracts and observability

Keep separate application contracts: `IGeneralNeedInterpreter`, `IConstructionProjectInterpreter` and `ISeapTenderMatchInterpreter`. Each user turn should normally use one model call. Capture operation, model/provider, prompt version, duration, success/failure, token count, need/project ID, clarification count, fallback and user correction—never secrets or unnecessary request content.

`IGeneralNeedInterpreter` returns only a non-binding `SuggestedProcurementMode` (`ConstructionProjects` or `SeapTenderSearch` when appropriate). The shared Procurement Core remains in its current flow until the user makes an explicit choice; this keeps construction/SEAP detection out of routing and persistence.

Before Task 9, the Construction interpreter is a routing/interpretation boundary only. Preserve the existing Construction project state and compatible request fields exactly as they are; do not add temporary generic fields to `Rfq` to store new Construction facts.

## Routing

Critical business states should be refreshable, back-safe and directly addressable where meaningful. Not every transient dialog needs a route. Buyer Home, My Requests, offer comparison, provider opportunity/request and claim continuity are critical paths.

## V3 — Auto-bidding (2026-08)

A new, configuration-gated auto-bidding module extends the modular monolith without touching the Procurement Core:

- **SEAP ingestion** (`Seap` config): a background worker polls the public e-licitatie.ro notice-search API (`POST /api-pub/NoticeCommon/GetCNoticeList/` with a JSON filter of `sysNoticeTypeIds`) and imports them as a distinct `SeapTender` aggregate. Notice types 2 (CN) and 17 (SCN — simplified procedure, where commune/town tenders such as „PRIMARIA COMUNEI POIANA DAMBOVITA" live) are queried. SEAP tenders are public opportunities, not CompaSpot buyer needs — the buying institution is external and never becomes an ApplicationUser, so tenders deliberately do not reuse `Rfq`. **Published documents** (Fișa de date, Caiet de sarcini, formulare, model contract — the notice-search payload does not carry them) are resolved at import from the public notice-detail API (`GET api-pub/NoticeCommon/GetDfNoticeSectionFiles/?initNoticeId=&sysNoticeTypeId=`, the same call the SPA uses) and stored as `SeapTenderAttachment` records holding the **remote e-licitatie.ro file URL**; the download endpoint proxies them on demand (same-origin Referer). Because the search payload does not carry documents, the numeric `noticeId`/`sysNoticeTypeId` are persisted on the tender (ADR-012), so the documents can be resolved again later: the detail page fires `POST /api/v1/seap/tenders/{id}/documents` once when the „Documente Originale" tab is opened empty (idempotent; 503 + „Reîncearcă" on failure), and the on-demand „Caută în SEAP" search doubles as a self-heal — an already-imported tender without documents gets its notice id backfilled and its list refreshed. Data sources: when the live endpoint responds it delivers **current** notices (observed live: `SCN1179142`, published 26.08.2026); the anonymous search can cap its result (`searchTooLong`) and sometimes returns only a partial slice, and in local Development `Seap:LocalFallbackEnabled` falls back to the golden payload under `App_Data/SeapMocks/` (a verbatim capture containing April-2019 notices) when the live endpoint is unreachable or non-JSON.
- **SEAP enrichment and filtering**: each notice keeps both the CPV code and its human-readable label (`CpvNames`, e.g. "Montare de garduri" from `45342000-6 - Montare de garduri (Rev.2)`) and a `County` derived deterministically from the contracting-authority name (`CountyParser`, 42-county alias table — no AI, e.g. "... VASLUI" → Vaslui, "MUNICIPIUL CLUJ-NAPOCA" → Cluj). The AI categorizer (`SeapCategorizerService`, `ILlmProvider`) maps the CPV label to a CompaSpot category; the first tender per standardized CPV code pays one LLM call and the `CpvCategoryMapping` table serves every later one. Categories the LLM returns that do not exist yet are auto-created under the "Achiziții generale" root. Every failure degrades to null — the tender still imports. The Anunțuri SEAP UI filters only by SEAP parameters — CPV prefixes and counties (ADR-009, persisted on `SupplierProfile` as `SeapCpvPrefixes`/`SeapCounties`) plus the optional SEAP interest `MarketRadiusKm` (county-seat-to-county-seat, `CountyDistance`) — and is isolated from the B2B `Category` entity (the marketplace product-category checkboxes are not rendered; backend `ListTendersAsync` still supports `categoryIds` with the AI-mapped `CategoryId` authoritative and the CPV-prefix match as fallback for other callers). CPV matching is class-wide: `CpvPrefix.ToMatchPattern` widens a prefix to its 4-digit class (whole divisions to 2 digits) so representative codes (`45210000`, `45233000`) match granular tender codes (`45214200-2`, `45233100-2`). A **„Caută în SEAP"** action (`search=true&from&to`) takes the active parameters and pages the live e-licitatie.ro search — honoring the publication-date window (`startPublicationDate`/`endPublicationDate`, verified live: `2026-01-01` returns current-year notices; the default unfiltered query returns a stale 2019 slice) — derives each notice's county deterministically, imports only the matching notices (no LLM categorization, no attachments), and re-filters the local list. Defaults to the current year; "Tot istoricul" leaves the window open. Because the anonymous search caps wide windows at ~3000 notices with an unstable slice (a recent matching notice can be missing from one scan and present on the next — verified live with SCN1179140, Brașov, published 26.08.2026), the search additionally scans the trailing 30 days (clamped to the requested window) as a reliable complement. Tenders without a recognizable county are excluded only while a radius filter is active. The discovery feed (`ListTendersAsync`) returns **only procedurally open tenders** (`Deadline >= now`) — closed procedures are not bid targets and would only clutter the list. The **AI detail extraction** (`SeapSummaryService`, `ILlmProvider`, never a gate) runs at every import — background poll and on-demand search alike — and feeds the notice data the importer holds (title, CPV, estimated value, buyer, county, deadlines, description when present; the text of already-processed Fișa de Date / Caiet de Sarcini attachments when the pipeline extracts it) to the LLM, which returns a strict JSON contract: `summaryPoints` (max 5 „Sinteză AI" bullets, 140 chars each), plus `awardCriterion`, `participationGuarantee`, `fundingSource`, `contractDuration`, `qualificationRequirements`, `keyPersonnel` and a 2–3 sentence acquisition `description` (null when the notice does not state the fact — the LLM must never invent data). Values persist on `SeapTender` (additive migration `AddSeapAiDetailExtraction`: `SummaryPoints` as `text[]`, the rest as `text`); the 2–3 sentence AI description fills `SeapTender.Description` only when the notice's own full text is absent. Any LLM/parse failure leaves the tender without AI details but fully usable. The detail page (`GET /api/v1/seap/tenders/{id}`) maps them into `SeapTenderDetailsDto`, and `POST /api/v1/seap/tenders/{id}/summary` regenerates the extraction on demand for tenders that still lack one (idempotent; 503 with a friendly `detail` on failure). The „Sinteză AI" card is an honest state machine — real bullets, a skeleton only while a genuine on-demand request runs, an actionable „Generează sinteza AI" empty state, and a recoverable error with deliberate retry — never an endless fake-progress skeleton; the detail rows keep placeholders until the extraction is present.
- **Depozit de Documente (Company Vault)** (`CompanyVault`/`VaultDocument`/`DocumentChunk`): PDF uploads, optional Azure Document Intelligence OCR, overlapping chunking, optional OpenAI embeddings stored in a `vector(1536)` column (pgvector). The RAG query orders `DocumentChunks` by cosine distance (`<=>`). Azure Document Intelligence is known to **truncate full-document analysis to ~2 pages** for PAdES-signed / large PDFs when page 1 is included (verified 2026-08-27 against the live endpoint). `AzureDocumentIntelligenceExtractionService` therefore counts the real physical pages with PdfPig, runs the full-document pass first, and when the returned page count is lower it re-analyzes in **chunks of 2 pages** and merges by page number keeping the longest text per page (`MergeAndOrderPages`).
- **Bidding engine** (`Bidding`): embeds tender requirements → top-N chunk retrieval → Anthropic Claude (`ILlmProvider`, mocked in tests) → strict JSON parsing → `.docx`/`.xlsx` generation (`IDocumentGenerator`) → S3. The LLM prompt requires **all numbered points** of the Caiet de sarcini and a `financialSummary` array copying the recap totals (T1–T4, TOTAL GENERAL, TVA); when present, `DocumentGenerator` renders the recap below the TOTAL row of the `.xlsx` ("Recapitulație financiară").
- **Stripe checkout** (`Stripe` config): dynamic `PriceData` from the fair-pricing EUR tiers (`PricingCalculator` — <20k€ 25€, 20k–100k€ 75€, 100k–500k€ 300€, 500k–1M€ 500€, 1M–5M€ 1.000€, 5M–10M€ 2.000€, then 3.000€ per additional 5M€ band up to 50M€ → 10.000€, ≥50M€ 20.000€; the SEAP estimated value in RON is converted with `AutoBidding:RonToEurRate`, default 5). **The first generation per account is free** (`ApplicationUser.FreeGenerationsRemaining`, default 1; migration `AddFreeGenerationsRemaining`). Webhook verifies `Stripe-Signature` and triggers generation, `bid-status` is polled, and the UI shows the dynamic price / free-generation state via `GET /api/v1/seap/tenders/{id}/pricing`.
- **Shadow Mode** (`AutoBidding:IsShadowMode`): generates silently, skips Stripe, exposes nothing to end users — the switch for safe real-data rehearsal before go-live.
- **Standalone product surface**: the SEAP experience (**Anunțuri SEAP**) is a permanent Main Menu item for authenticated users — never context-gated; its routes (`/seap/tenders`, `/seap/tenders/{id}`) also keep the company rail for continuity. The SEAP list page exposes an **Admin-only** (role `Administrator`) Caiet de sarcini test surface at the top: it uploads a specification PDF straight into the `AutoBiddingService` pipeline (`POST /companies/{id}/vault/specifications` + regenerate), showing the generated `.docx`/`.xlsx` download links — the manual validation path for the pipeline without leaving the app. The list also shows a **SEAP Tender Match** filter card (CPV + județe chips) and an AI chat entry (`/seap/match`, ADR-009) that persists the confirmed filters on the company profile.
- **MVP surface flag** (`Features:MarketPlaceEnabled`, SSM `features-marketplace-enabled`, false): every marketplace surface (live market, RFQs, offers, profiles, messaging, notifications, supplier discovery) is hidden from navigation and its routes redirect to `/seap/tenders`; Admin stays. **Cont** (`/account`) and **Firma** (`/account/company/*` — create/register and edit the companies the user represents) remain reachable because SEAP auto-bidding needs the company data; the SEAP list page shows an „Înregistrează firma" CTA when the user has no company. The SEAP radius filter reads `SupplierProfile.MarketRadiusKm` and is editable in Cont → Firma → setările firmei („Rază de interes pentru anunțuri"); saving it updates the SEAP list on the next load. The Firma page hides the marketplace sections („Categorii de produse" and „Zonă și rază de livrare") while `MarketPlaceEnabled=false` and instead shows a „Nișa ta SEAP" editor (CPV prefixes + counties chips) persisted via `PUT /api/v1/seap/tender-match/profile`. The SPA reads the flags from `GET /api/v1/features` (`FeaturesService`). The public landing (`/`) becomes a **SEAP SEO landing** targeting the purchase-intent keywords when the flag is off, and a public **Terms page** (`/terms`) carries the Limitation of Liability clause. Before every document download the user must accept the responsibility checkbox (Copilot positioning: assisted-drafting software, not legal/technical consulting). See ADR-008.

Every external dependency (SEAP API, S3, OCR, embeddings, Claude, Stripe) is behind an interface and disabled by default in `appsettings.json`; the platform starts and works without any of the V3 credentials. Integration tests now use a Testcontainers `pgvector/pgvector:pg17` instance instead of the local development database; the local compose database image was updated to `pgvector/pgvector:pg17` to match.

### Safety switches and cost guardrails (V3)

- **Feature flags** (`Features` section, hot-reloadable): `SeapIngestionEnabled` and `AutoBiddingEnabled` are master switches, both `false` at deploy. They are read through `IOptionsMonitor`, so a config change takes effect within about a minute **without a redeploy**; the base MVP application never depends on them.
- **LLM/S3 cost guardrails**: `max_tokens` is hard-capped at 16000 inside `AnthropicClaudeProvider` regardless of configuration (raised from 4000 because a full 14–20 page Caiet proposal with BOQ + financial recap exceeds 4000 output tokens and the JSON would be truncated mid-array); the SEAP scraper imports at most `Seap:MaxNewNoticesPerHour` (default 5) new tenders per rolling hour; Claude and Azure Document Intelligence each run a consecutive-failure circuit breaker (3 failures → open for one hour, calls fail fast while open). Pipeline failures that carry a user-facing message (`AutoBiddingPipelineException` — e.g. scanned/illegible PDF, missing Azure/Claude config, truncated or Markdown-wrapped LLM JSON) are mapped to `ProblemDetails` with a friendly `detail` by `AutoBiddingExceptionHandler`, so the SPA shows a specific alert instead of a generic 500. The auto-bid prompt demands JSON-only output and `BiddingJsonParser` additionally tolerates Markdown prose (``` fences, leading `#` headings, trailing notes) by falling back to the outermost JSON object. The upload/generate endpoints accept an optional `progressRequestId`; a singleton `IPipelineProgressStore` records each stage (Extracting → Generating → Finalizing → Completed/Failed) and `GET .../vault/specifications/progress/{requestId}` lets the frontend show real per-step progress ("Etapa 1/3…", "Etapa 2/3…") while the 30–60s request runs.
- **Staging ingestion** (`SeapRawIngestion`): raw notices land first in a staging table (`Pending`), and are promoted to the public `SeapTenders` table only after parsing succeeds (`Parsed`); failures keep the payload and `ErrorMessage` (`Failed`). Live users never see half-processed announcements.
- **Non-breaking migrations**: every V3 migration is additive (new tables, new nullable columns); no existing column is dropped or renamed in the same step.

### Local-first developer experience

Development (`appsettings.Development.json`) runs with **zero cloud credentials**; every external
dependency is behind an interface with a local default. `Storage:UseLocalStorage=true` swaps the
shared `IStorageService` (used by SEAP attachments and the Company Vault) to `LocalFileStorageService`
(disk under `App_Data/Storage/`) instead of `CloudflareR2StorageService` (R2/AWS S3); `AI:UseMockProvider`
swaps `ILlmProvider` to `StaticMockLlmProvider` (preset JSON) instead of `AnthropicClaudeProvider`;
the SEAP importer uses the **live e-licitatie.ro endpoint in every environment** — Development mirrors
Staging/Prod and never falls back to golden payloads at runtime, so local validation is relevant to
production (the golden payloads under `tests/Fixtures/` remain **test-only** fixtures for the notice-parser
regression suite). Development additionally sets `Features:SeapIngestionEnabled=true` so the SEAP worker
imports against the real endpoint (Prod/Staging toggle the same flag at deploy); and the EF migrations are
applied automatically at startup in Development (Prod/Staging migrate through the explicit migration
bundle). Development mirrors the Staging/Prod auto-bid flow out of the box: `Features:AutoBiddingEnabled`
and the real `AnthropicClaudeProvider` (key via user-secrets) with the Staging/Prod model/token settings
in shadow mode, so the complete generation can be exercised locally before any deploy (`AI:UseMockProvider`
reverts to the zero-cost mock). See `README.md` → "Local provider matrix".
